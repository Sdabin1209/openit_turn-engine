# 0001. turn-engine은 서비스가 아니라 라이브러리로 둔다

- 상태: 수용(2026-10-28 소급 기록. 결정 자체는 D06, D22, D75-3)
- 관련: `head/docs/DECISIONS.md` D05, D06, D22, D49, D75 / `head/docs/STRUCTURE.md` 규칙 4 / `docs/boundary.md` 1절

## 맥락

LoRA-A 출력이 의미 규칙을 지키는지 검사하는 로직이 필요하다. 이 로직을 호출하는 곳은 survey-service 한 곳이고(그 밖에 데이터셋 검증·시험에서 읽기), 호출은 모든 턴에서 일어난다. 영역 사이 호출은 HTTP가 원칙(D49)이므로 "별도 서비스로 만들 것인가"가 문제였다.

## 결정

프로세스, 포트, `/healthz`, 컨테이너 이미지가 없는 Python 라이브러리로 둔다. 소비자는 Git 태그 `v<ENGINE_VERSION>`으로 설치하고 자기 이미지에 고정한다.

## 왜

- 헤드의 API/SDK 선택 순서(`STRUCTURE.md` 규칙 4)의 첫 질문이 "같은 프로세스에서 같은 순수 로직이 필요하면 라이브러리"다. 이 로직은 입력만으로 결과가 정해지는 순수 계산이고 호출자 프로세스 안에서 돈다.
- 턴마다 부르는 검사에 네트워크 왕복을 넣으면 지연과 실패 지점(timeout, 재시도, 인증)만 늘고 얻는 것이 없다. 이 검사가 실패하면 그 턴이 막히는 위치이므로 실패 지점이 적을수록 좋다. (이 문장의 앞부분은 설계 판단이며, 지연을 측정한 기록은 없다.)
- D22(3): 라이브러리는 이미지가 아니라 Git 태그 패키지다. D18: 패키지 인덱스 서버 없이 Git 태그로 배포한다.
- 같은 버전이면 같은 결과이므로(ADR 0003) 게이트·합성 데이터·평가가 버전만 기록하면 재현된다. 서비스로 두면 "어느 서버 버전이 답했나"를 따로 기록해야 한다.

## 검토한 대안과 버리는 이유

| 대안 | 버리는 이유 |
|---|---|
| 독립 HTTP 서비스 | 위 이유(지연·실패 지점·운영 대상 증가). 상태가 없고 호출자 한 곳이라 분리 이득이 없다. 근거 기록: 대안을 직접 비교한 문서는 찾지 못했고, 위는 STRUCTURE.md 규칙 4에서 따른 추론이다 |
| survey-service 안에 코드로 합침 | D06이 turn-engine과 model-runtime을 별도 라이브러리로 분리했다. 합치면 model-lab·synthetic-data·게이트가 같은 검사를 쓸 수 없고(영역끼리 코드를 가져오지 않는다), 서비스 안의 코드는 재사용하려면 복사해야 한다 |

## 결과

- 얻는 것: 서버·이미지·`/healthz` 부담 없음, 네트워크 실패 없음, 다른 영역 없이 혼자 시험 가능(메모리 구현이 따로 필요 없음).
- 감수하는 것: 소비자 이미지를 다시 빌드해야 규칙 변경이 반영된다. 서비스 단위 배포·롤백이 아니라 소비자 이미지의 의존 태그 변경으로만 바뀐다. 릴리스가 `turn_engine_version`을 기록하고 MAJOR.MINOR가 다르면 적재를 거부한다(D46, D80).

## 되돌리는 조건

호출자가 둘 이상의 서로 다른 프로세스 언어가 되거나(Python 외 소비자), 규칙을 이미지 재배포 없이 바꿔야 할 요구가 생기면 서비스화를 다시 검토한다. 지금 그런 요구는 기록에 없다.
