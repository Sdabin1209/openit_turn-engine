# 0004. 규칙 I8의 범위: A 출력의 의미 검증 안전망

- 상태: 수용(범위 확장은 미정, 0002의 TE-1)
- 관련: D75(3), `boundary-contracts/INTERFACES.md` I8 / `docs/boundary.md` 8-1

## 맥락

D74로 정규화·판정·기록·Plan이 LoRA-A로 옮겨 갔다. I8(turn-engine 인터페이스)을 폐기할지, 다른 역할로 남길지 정해야 했다.

## 결정

I8은 폐기가 아니라 **LoRA-A 출력의 사후 의미 검증 라이브러리로 대체**한다(D75-3). 범위는 다음 다섯 규칙과 두 가지 추가 위반 코드뿐이다.

- 규칙: (a) `targets`는 `values`의 키, (b) `next_item`은 action별 규칙과 문항 순서·건너뛰기를 따른다, (c) 건너뛰기를 어기거나 조건 없이 건너뛰면 `SKIP_ORDER_MISMATCH`, 그 밖은 `NEXT_ITEM_MISMATCH`, (d) `save`는 ANSWERED·CORRECTION일 때만 true이고 MISSING·UNCLEAR·UNKNOWN·REJECTED의 `value`는 null.
- 추가 코드: `OUTPUT_SCHEMA`(안전망으로 형식 위반도 예외가 아니라 보고), `UNKNOWN_ITEM`(문항 순서 표에 없는 문항). I8 초안의 예에 turn-engine이 더한 것이다(제안으로 표시).
- 입력(`ActionExtractionInput`) 위반은 예외(`ContractViolation`)다. 호출자의 조립 결함이므로 재시도가 무의미하다.

값의 타당성은 범위 밖이다(ADR 0002).

## 왜

- 모델이 낸 `next_item`이나 `save`가 틀리면 잘못된 문항을 건너뛰거나 틀린 값이 저장된다. 이 둘은 스키마 키워드로 표현할 수 없는 조건 규칙이라(D48) 사후 검증이 필요하다.
- 폐기하고 서비스 코드에 넣으면 규칙이 서비스 안에 묻혀 평가·데이터 생성 쪽 검증과 어긋날 수 있다. 라이브러리로 두면 같은 규칙을 모두가 쓴다(ADR 0001).
- 범위를 이 정도로 좁힌 이유는 문진 스키마(칸 정의)가 turn-engine 소관이 아니기 때문이다(ADR 0002). 규칙 문장이 현재 코드와 일치하는지는 점검 D1이 확인했다.

## 검토한 대안과 버리는 이유

| 대안 | 버리는 이유 |
|---|---|
| I8 폐기 | 의미 검증을 할 곳이 없어진다. 모델이 틀릴 수 있다는 전제(D75-1)에 반한다 |
| v1 Plan을 검증 기준으로 유지 | v1 로직은 경우의 수 대응이 문제였다(D74 근거). 모델의 출력과 다시 비교하는 이중 구현이 된다 |
| 입력 위반도 위반 목록으로 반환 | 입력 조립 결함과 모델 출력 결함을 호출자가 구분할 수 없게 된다. 근거 기록: 이 선택의 명시적 이유는 `boundary.md` 5절의 표(재시도 무의미)뿐이다 |

## 결과

위반이 하나라도 있으면 survey-service는 `OUTPUT_INVALID`와 같게 처리한다. 범위가 좁아 `DATASET_V2_FLOW`(31문항·건너뛰기 7건, 시험용 고정값, D99) 같은 시험용 표로 학습 데이터 전수 검증이 가능하다.

## 되돌리는 조건

TE-1의 규칙 확장(헤드 결정 대기), 또는 `QuestionFlowTable`을 문진 스키마에서 만드는 변환(CR-010)이 확정되면 범위를 갱신하고 이 ADR을 `Supersedes`로 잇는다.
